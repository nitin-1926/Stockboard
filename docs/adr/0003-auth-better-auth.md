# 0003. Auth: Better Auth (Google), per-request roles, share links outside the auth library

- Status: Accepted
- Date: 2026-11-11

## Context

Stockboard has one owner, a few invited people (contributor or viewer, optionally "hide amounts"), and anonymous read-only share links. Access must be revocable immediately, and the old app's failure mode (role checks in the UI and in a layout, a share path that skipped redaction) must not recur. Constraints: zero cost, Next 16 with Cache Components (`proxy.ts`, no segment `runtime` exports), Neon Postgres through one WebSocket `Pool` (ADR-0004).

## Options considered

1. Auth.js / next-auth v5: maintenance-only since 2025-09 and v5 never left beta.
2. Clerk / hosted auth: free tier is fine today, but it adds an external account store and vendor lock-in for a single-owner app.
3. Better Auth 1.7: open source, first-party Drizzle adapter (`provider: "pg"`) on our existing Pool, `databaseHooks.user.create.before` can veto sign-up, `nextCookies()` for Server Actions.
4. Roles stored on the Better Auth `user` row (admin plugin) vs. resolved per request from `OWNER_EMAIL` + an `access_grants` table.
5. Share links as Better Auth anonymous users vs. our own `share_links` table + signed cookie.

## Decision

Better Auth (3) with Google only, and everything access-related kept outside it:

- **Sign-up gate:** `user.create.before` allows `OWNER_EMAIL` (case-insensitive) or an email with an active grant; otherwise it throws `APIError` (`NOT_INVITED` / `ACCESS_EXPIRED`), so no user row is created and the sign-in page shows the reason.
- **Roles resolved per request** (`src/lib/auth/access.ts`): owner if the session email equals `OWNER_EMAIL`, else the role of an active grant, else no access (the user's sessions are deleted). Nothing is cached in the session, so revoke/expiry applies on the next request. Grants are keyed by lowercased email with no FK to `user`, because an invite exists before the first sign-in.
- **Data-access-layer enforcement:** every view and server action calls `requireActor()` / `authorize(action)`. `proxy.ts` only checks cookie presence; layouts make no access decisions.
- **Share links** (`share_links`): 32-byte base64url token, only its sha256 stored. `/s/<token>` sets an httpOnly cookie `sb_share = <linkId>.<HMAC-SHA256(SHARE_LINK_SECRET)>`; every request re-validates the row. A share link is always a viewer: the table has no role column and the resolver never reads one.
- **Hide amounts** is server-side redaction (`src/lib/auth/redact.ts`): per-view field policies delete amount fields from DTOs, so restricted payloads never contain them.

## Consequences

- One extra grant query per request for non-owners; acceptable at this scale.
- Better Auth tables (`user`, `session`, `account`, `verification`) are generated by `auth generate` into `src/db/schema/auth.ts`; regenerate after a Better Auth upgrade that changes its schema.
- Sessions use no cookie cache, so revocation is immediate at the cost of one session lookup per request. Revisit if latency matters.
- Preview deployments have changing URLs; Google OAuth only works on origins registered as redirect URIs, so previews can't sign in unless a stable preview domain is registered.
- Every new view must declare a `FieldPolicy` and a redact test (pattern documented in `redact.ts`).
